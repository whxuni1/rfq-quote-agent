# 产品原则

本文件说明这个报价 Agent 什么该做、什么不该做。执行图见 `architecture.md`，字段见 `02-shared-schemas.md`，完成线见 `acceptance-criteria.md`。

## 它是什么

面向智能座舱与智驾硬件的执行主体。输入是 RFQ 包：PDF 技术规格、Excel BOM、图纸引用。输出是报价草稿包：报价函、成本明细、风险登记、假设、例外清单、评审轨迹。对象包括 SoC、显示、摄像头模组、传感器、PCBA、连接器、结构件、线束、热管理、光学和软件许可。

它不是聊天机器人，也不代替采购员下单。

## 原则

1. **文档进，文档出。** 不连接 ERP、PLM 或供应商系统。解析、should-cost、汇总和渲染都是纯函数。
2. **数字不交给模型。** 模型负责理解、拆分、风险判读和报价函措辞。单价、毛利、汇总和 gate 判定由工具与规则完成。同一输入、同一 schema，结果可复现。
3. **四个专业角色，一个编排者。** 工程、采购、财务、商务并行读同一份 BOM，经 Blackboard 交回。它们不互相调用。只有 Orchestrator 推进状态。
4. **关键决策停给人。** 毛利底线、关键单源、高规格缺口、大额 NRE、超标准保修、关键条款缺口、高歧义和数据缺失，都走 Review Gate。别处不再“顺便”问人。
5. **结构先于散文。** 报价先落成 `QuoteDraft`，再渲染成函件。自由文本不是交付物。
6. **类型是合同。** 跨模块数据只存在于 `schemas/` 的 Pydantic v2 模型。金额是非负 `Decimal`，精度 4 位。
7. **可核对。** 三个金样例是交付门槛：成本容差、风险全捕获、gate 按预期触发。工具层覆盖率目标高于整体。
8. **小步，且不越界。** 一次任务一个 PR。任务描述与 schema 冲突时停下来提问，不另造字段或 API。

## 明确不做

- 把四个 sub-agent 收成一个大 prompt 顺序询问。
- 用模型计算成本。
- 在 gate 之外改价格、条款或毛利。
- 为了跑通而调用不存在的库。
